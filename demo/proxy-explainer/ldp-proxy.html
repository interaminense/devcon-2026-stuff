DEVCON 2026 · LDP Headless API

LDP GraphQL Proxy

How a page in DXP reads Liferay Data Platform data without ever holding an LDP credential.

POST /o/analytics-rest/v1.0/graphql DXP 2026.Q2+ No feature flag
The path

Two hops, two different credentials

The browser only ever talks to DXP. DXP is the only one that talks to LDP, and it signs that call with the workspace secret it keeps on the server.

Step by step

What each side does

1

Browser to DXP

The page posts a standard GraphQL body to its own origin. DXP treats it like any headless call: the user must be authenticated. In the browser that is the session cookie plus x-csrf-token; from a script, Basic Auth or OAuth2.

2

Inside DXP

GraphQLResourceImpl loads the Analytics configuration of the current company: the values saved when the instance was connected to LDP in Instance Settings. It does not look at the query or check any permission.

3

DXP to LDP

AnalyticsCloudClient posts the same body to <Faro backend URL>/api/1.0/graphql with the workspace headers below. LDP checks the signature and scopes the data to that project.

4

Back to the browser

DXP returns LDP's body and status code as they are, typed as JSON. If LDP cannot be reached, DXP answers 502 with Unable to reach Analytics Cloud.

Hop 1 · Browser to DXP

The call the page makes

From the DEVCON demo card. No LDP token, no LDP host: only a relative URL and the CSRF token DXP already put on the page.

const response = await fetch('/o/analytics-rest/v1.0/graphql', {
	body: JSON.stringify({
		query: `query ($channelId: String!, $rangeKey: Int) {
			site(channelId: $channelId, interval: "D", rangeKey: $rangeKey) {
				visitorsMetric { value previousValue trend { percentage } }
			}
		}`,
		variables: {channelId: CHANNEL_ID, rangeKey: 7},
	}),
	headers: {
		'Content-Type': 'application/json',
		'x-csrf-token': Liferay.authToken,  // proves the call comes from a DXP page
	},
	method: 'POST',
});
Who is callingHow DXP authenticates it
Page in the browserSession cookie + x-csrf-token header. What the demo uses.
Script or serverBasic Auth (-u user:password) or an OAuth2 token for the Liferay.Analytics.REST application.
Visitor, not signed inRuns as Guest. No default Service Access Policy lists this endpoint, so DXP answers 403 before the proxy runs.
Hop 2 · DXP to LDP

What DXP adds on the server

Every value comes from the LDP connection saved for the company. None of them is ever sent to the browser.

Security

Why there is no anonymous access

DXP to LDP Always required

LDP has no public endpoint. Every call needs the project ID, data source ID and security signature. This is not configurable, and it is why the proxy exists: the secret stays on the DXP server instead of in the page.

Browser to DXP Default, configurable

Requiring a signed-in user is DXP's default for headless APIs. An admin could open the endpoint to Guest with a Service Access Policy allowing GraphQLResourceImpl#postGraphQL. Don't: the endpoint has no permission check, so anyone on the internet could read the whole workspace, signed as your DXP.

Say

There is no way to read LDP without a credential. DXP keeps the workspace secret and asks for a signed-in user. An admin could open the endpoint to guests, but it does not filter by permission, so that would publish the whole workspace.

Checklist

What you need to use it

  1. DXP 2026.Q2 or laterThe module arrived with LPD-85945 and is not in 2026.Q1. No feature flag.
  2. DXP connected to LDPInstance Settings → Platform → Analytics Cloud. The connection saves the URL, IDs and signature the proxy uses.
  3. A signed-in userSession + CSRF token in the browser, or Basic Auth or OAuth2 from scripts. Any user of the instance works; there is no role check.
  4. A channel ID in the queryOne LDP property is one channel. Copy it from the LDP Sites URL and pass it as channelId.
